<h2 id="swift-package-manager">Move to Swift Package Manager</h2>

2.0 ships no CocoaPods pod and no Carthage framework. Swift Package Manager is the only packaged distribution channel.

If you install ably-cocoa with CocoaPods or Carthage, that is the largest part of this migration, because it changes your dependency manager rather than a line of your code. Both channels stay on the 1.x line, which continues to receive security and critical fixes; to move to 2.0, add the package to your project through Swift Package Manager instead.

<h2 id="deployment-target">Raise your deployment target and use Xcode 26</h2>

2.0 requires macOS 12, iOS 15 or tvOS 15. Raise your deployment target before updating.

The package needs Swift 6.2 to build, so build with Xcode 26 or later.

<h2 id="imports">Depend on `AblyPubSubDevice` and update your imports</h2>

The package vends two products: `AblyPubSubDevice`, which is the SDK, and `AblyLiveObjects`. Change the product your target depends on from `Ably` to `AblyPubSubDevice`, then update every import:

| 1.x | 2.0 |
|---|---|
| `import Ably` | `import AblyPubSubDeviceSwift` |
| `@import Ably;` | `@import AblyPubSubDevice;` |
| `#import <Ably/Ably.h>` | `#import <AblyPubSubDevice/AblyPubSubDevice.h>` |

In Swift, `AblyPubSubDeviceSwift` is the module to import. It includes the whole SDK and adds `async` versions of operations such as `attach`, `publish` and presence `enter`, which throw an `ErrorInfo`:

```swift
try await channel.attach()
let result = try await channel.publish("greeting", data: "hello")
```

The SDK on its own is still the `AblyPubSubDevice` module, which Swift can also import, without the `async` functions. In code that imports `AblyPubSubDeviceSwift`, a call such as `channel.attach()` made inside an `async` function resolves to the `async` version and needs `try await`.

<h2 id="factory">Create clients through the device factory</h2>

A client is created through `PubSubDevice`:

```swift
let options = ClientOptions(key: "your-ably-api-key")
let client = PubSubDevice.createClient(options: options)
```

`createClient(key:)` and `createClient(token:)` take a key or token string directly.

A client built this way tells Ably that it runs on an end user's device. That declaration determines how the connection is counted: on an account billed by monthly active users, device traffic counts toward the total, the connection must carry a `clientId`, and that `clientId` is subject to a concurrency limit.

The client class's initializers are no longer part of the public API, and neither are the `createWithOptions:`, `createWithKey:` and `createWithToken:` class factories, which are removed. Replace every `ARTRealtime(options:)` with a call to the factory.

<h2 id="renames">Handle the renamed types</h2>

The REST family is named for the protocol it speaks, and the top-level realtime class is named for the product:

| 1.x | 2.0 |
|---|---|
| `ARTRealtime` | `ARTPubSubClient` |
| `ARTRealtimeProtocol` | `ARTPubSubProtocol` |
| `ARTRest` | `ARTHttpClient` |
| `ARTRestChannel` | `ARTHttpChannel` |
| `ARTRestChannels` | `ARTHttpChannels` |
| `ARTRestPresence` | `ARTHttpPresence` |
| `ARTRestAnnotations` | `ARTHttpAnnotations` |

`ARTRealtimeChannel`, `ARTRealtimeChannels`, `ARTRealtimePresence` and `ARTRealtimeAnnotations` keep their names, as do the connection and channel state enums.

The HTTP client family is no longer documented API. `ARTHttpClient` and its channel, presence and annotations classes moved to internal types, which cover API intended for Ably-authored SDKs, and they can no longer be constructed from outside the SDK. An application reaches Ably through the realtime client returned by the `PubSubDevice` factory.

<h2 id="swift-names">Drop the `ART` prefix in Swift</h2>

Swift sees the SDK's types without the prefix. `ARTClientOptions` is `ClientOptions`, `ARTErrorInfo` is `ErrorInfo`, `ARTMessage` is `Message`, and so on. Objective-C is unchanged and keeps the prefix everywhere.

Two of the new names are also declared by Apple's frameworks: `Annotation` by SwiftUI and MapKit, and `Cancellable` by Combine. In a file that imports one of those alongside this SDK, write `AblyPubSubDevice.Annotation` to say which you mean.

<h2 id="removals">Stop using the API that 2.0 removes</h2>

These members were deprecated in 1.x and are removed:

- `ARTClientOptions.fallbackHostsUseDefault`. Set `fallbackHosts` directly if you need a custom list.
- `ARTConnection.recoveryKey`. Use `createRecoveryKey` instead, which it aliased.
- `ARTStats.intervalGranularity`.

These were not marked deprecated but are removed too:

- `ARTFallbackIncompatibleOptionsException`, which only the removed `fallbackHostsUseDefault` guards could raise.
- `ARTPush`'s four class methods taking a `rest:` parameter. Use the `pubsub:` overloads, which take the client the factory returns.
- `ARTRealtimeInstanceMethodsProtocol`. `ARTPubSubProtocol` now declares its methods, and its initializers are gone, so use `ARTPubSubProtocol` instead.
- The `publish` overloads that take a `clientId` or `extras` argument alongside `name` and `data`. Set them on a `Message` and publish that instead: `channel.publish([Message(name: "event", data: data, clientId: "client")])`. For `extras`, set the message's `extras` property before publishing.
- `ARTPushRegistererDelegate.didAblyPushRegistrationFail:`, the update-failed callback that the spec deprecates (RSH3e3a). Implement `didUpdateAblyPush:` instead, which is called after every update of the device registration: with the error if it failed, or with `nil` if it succeeded. Both methods are optional, so the compiler won't flag an implementation of the removed one that you leave in. It just stops being called.

One behaviour change comes with the deletions: `ARTClientOptions.fallbackHosts` now uses a synthesised setter, which honours the property's `copy` attribute. The hand-written setter it replaces assigned without copying.

<h2 id="message-version-annotations">Build message versions and annotations through their initializers</h2>

`ARTMessageVersion` and `ARTMessageAnnotations` are immutable, so Swift treats them as `Sendable`. Their properties are read-only, and their `init` is no longer available.

A message received from Ably already carries both objects, so code that only reads them needs no change. If you build one yourself, for example in a test, pass its values to the initializer:

```swift
let version = MessageVersion(serial: "124", timestamp: nil, clientId: nil, descriptionText: nil, metadata: ["reason": "typo"])
let annotations = MessageAnnotations(summary: ["reaction:distinct.v1": ["total": 1]])
```

The initializers store copies of their arguments. Mutating a dictionary or string after passing it in leaves the object unchanged.

Decoding is stricter in two places. A `metadata` entry whose value is not a string is dropped, because the property's type allows only strings. A `summary` that is not a JSON object becomes an empty summary.

<h2 id="argument-errors">Pass valid arguments to history, stats and request</h2>

These methods no longer have an `error` parameter, and they return nothing:

- `history(_:callback:)` on `RealtimeChannel` and `RealtimePresence`
- `stats(_:callback:)` on `PubSubClient`
- `request(_:path:params:body:headers:callback:)` on `PubSubClient`
- `listSubscriptions(_:callback:)` on `PushChannel`

`stats(_:)`, which takes only a callback, returns nothing too, where it returned a `Bool`.

An invalid argument is a bug in the calling code, so these methods now raise `NSInvalidArgumentException`. Swift cannot catch it, and the app stops. These arguments raise:

- a query `limit` greater than 1,000;
- a query `start` that is later than its `end`;
- a `request` method other than GET, POST, PATCH, PUT or DELETE;
- a `request` body that is neither a dictionary nor an array;
- a `request` path that is empty or is not a valid URL;
- `listSubscriptions` parameters without exactly one of `deviceId` and `clientId`.

In Swift, drop the `try` from these calls. A `do`/`catch` around them no longer catches anything, so remove it too.

A history query with `untilAttach` set on a channel that is not attached does not raise. The channel can change state at any moment, so that case is not a bug in the caller. The callback receives an `ErrorInfo` with code 40000 instead.

`ARTDataQueryError`, `ARTRealtimeHistoryError` and `ARTCustomRequestError` are removed. Their numbers overlapped, so the same error code could mean different errors.

<h2 id="endpoint">Select the Ably endpoint with `endpoint`</h2>

`ARTClientOptions` has an `endpoint` option, which replaces `environment`, `restHost` and `realtimeHost`. Those three options are removed. So are `ARTDefault.restHost`, `ARTDefault.realtimeHost` and `ARTDefault.fallbackHostsWithEnvironment:`.

The client connects to one host for both REST requests and realtime connections, and `endpoint` picks it:

| `endpoint` | Primary host | Fallback hosts |
|---|---|---|
| not set | `main.realtime.ably.net` | `main.[a-e].fallback.ably-realtime.com` |
| a routing policy ID, such as `acme` | `acme.realtime.ably.net` | `acme.[a-e].fallback.ably-realtime.com` |
| a non-production routing policy ID, such as `nonprod:acme` | `acme.realtime.ably-nonprod.net` | `acme.[a-e].fallback.ably-realtime-nonprod.com` |
| a hostname, such as `host.example.com` or `localhost` | the hostname itself | none |

If you set `environment`, set `endpoint` to the same value. If you set `restHost` or `realtimeHost`, set `endpoint` to that host.

A client that sets none of these options connects to new hosts. In 1.x it connected to `rest.ably.io` and `realtime.ably.io`, with fallbacks at `[a-e].ably-realtime.com`. If your network restricts outgoing traffic by hostname, allow the hosts in the table above.

`fallbackHosts` still replaces the fallback hosts, and an empty array turns them off. A custom `port` or `tlsPort` also turns them off, as in 1.x.

With an empty `fallbackHosts` array, an unreachable host no longer fails the connection. In 1.x the connection moved to FAILED and stayed there until you called `connect()`. In 2.0 it moves to DISCONNECTED and retries, as it does for a hostname `endpoint`.

<h2 id="limits">Set the request timeout and message size limit in `ClientOptions`</h2>

`ARTDefault.realtimeRequestTimeout` and `ARTDefault.maxMessageSize` are removed. Their values are now `ARTClientOptions` properties, so each client can set its own:

| Option | Default | Meaning |
|---|---|---|
| `realtimeRequestTimeout` | 10 seconds | How long the client waits for Ably to answer a connect, heartbeat, attach, detach or close. |
| `maxMessageSize` | 65536 bytes | The largest publish the client sends. A larger one fails with error code 40009. |
| `maxFrameSize` | 524288 bytes | The largest HTTP request body or WebSocket frame. This option is new, and the client does not check requests against it. |

On a realtime connection, the `maxMessageSize` that Ably sends when the connection is established replaces the option. `ARTConnection.maxMessageSize` returns the limit in force.

A debug build of 1.x checked publishes against 16384 bytes, the sandbox limit, until a connection said otherwise. 2.0 uses `maxMessageSize` in every build.

<h2 id="agent">Know what your clients now report to Ably</h2>

The SDK identifies itself to Ably as `ably-pubsub-cocoa`, where 1.x sent `ably-cocoa`. A client created through `PubSubDevice.createClient` also sends a versionless `ably-pubsub-device` entry, which is how Ably knows the client runs on a device.

Both are visible in `ClientInformation.agents`, in the `Ably-Agent` HTTP header and in the `agent` query parameter of the realtime connection. If you match on the agent string anywhere — in your own logging, or in tooling that reads it — update those matches.

<h2 id="annotation-timestamp">Read `Annotation.timestamp` without unwrapping</h2>

`ARTAnnotation.timestamp` is no longer nullable, because Ably sets it on every annotation it delivers. In Swift its type is `Date` rather than `Date?`, so remove any `if let`, `guard let` or `?` you use to unwrap it.

<h2 id="subscribe-listener">Use the listener that `subscribe` returns without unwrapping</h2>

The `subscribe` methods on `RealtimeChannel`, `RealtimePresence` and `RealtimeAnnotations` always return an `EventListener`. In Swift the return type is `EventListener` rather than `EventListener?`, so remove any `!`, `if let` or `guard let` you use to unwrap it before passing it to `unsubscribe`.

Subscribing on a channel in the FAILED state now registers the listener. In 1.x it returned `nil` and dropped the listener. The attach callback still receives an error, unless `attachOnSubscribe` is `false`, in which case it is not called. Either way, the listener receives messages once you attach the channel again. An annotation listener receives annotations only if the channel was attached with the `ChannelMode.annotationSubscribe` mode granted.

<h2 id="stats">Read stats from `entries`</h2>

`ARTStats` no longer has typed properties. Every statistic is in `entries`, a dictionary keyed by the statistic's name:

| 1.x | 2.0 |
|---|---|
| `stats.inbound.all.messages.count` | `stats.entries["messages.inbound.all.messages.count"]` |
| `stats.outbound.realtime.messages.data` | `stats.entries["messages.outbound.realtime.messages.data"]` |
| `stats.channels.peak` | `stats.entries["channels.peak"]` |

The names follow the JSON schema at `stats.schema`. A statistic with no recorded value is absent from `entries`, where 1.x reported `0`.

`ARTStatsMessageCount`, `ARTStatsMessageTypes`, `ARTStatsMessageTraffic`, `ARTStatsResourceCount`, `ARTStatsConnectionTypes`, `ARTStatsRequestCount` and `ARTStatsPushCount` are removed. So are `ARTStats.count`, `dateFromInProgress`, and the class methods `dateFromIntervalId:`, `granularityFromIntervalId:` and `toIntervalId:granularity:`.

`ARTStats` gains `unit`, `schema` and `appId`. `inProgress` is now nullable, because only an interval that is still in progress has one. In Swift, `intervalTime` is a property rather than a method, so drop the `()`.

<h2 id="extras">Read and set `extras` as a dictionary</h2>

`extras` on `ARTMessage`, `ARTPresenceMessage`, `ARTAnnotation` and `ARTOutboundAnnotation` is an `NSDictionary<NSString *, id>`, which Swift sees as `[String: Any]?`. In 1.x it was `id<ARTJsonCompatible>`, so you had to call `toJSON` to read it.

Read the dictionary directly instead of calling `toJSON`. If you passed `extras` as a JSON string, parse it into a dictionary first. A JSON string used to be sent to Ably as a string rather than as the JSON object that `extras` must be.

Received `extras` that are not a JSON object are now dropped, so `extras` is `nil` for them.

<h2 id="underlying-errors">Find system errors under the `ErrorInfo`</h2>

When a system error stops an operation, for example a network failure, the SDK still reports an `ErrorInfo` in `ablyErrorDomain`. In 1.x that `ErrorInfo` kept the system error's `code`, such as `-1001` from `NSURLErrorDomain`, and moved its domain into `userInfo`. In 2.0 its `code` is an Ably error code, and the system error is its underlying error:

- When the realtime connection's transport fails or disconnects because of a system error, or without giving one, the connection's reason has `code` `ErrorCode.disconnected` (80003) and `statusCode` 400.
- Otherwise, `code` is `ErrorCode.timeoutError` (50003) when an HTTP request timed out, and `ErrorCode.internalError` (50000) for anything else, with `statusCode` 500.
- `message` is the system error's `localizedDescription`.
- The system error itself, with its own domain and code, is in `underlyingErrors`, under `NSUnderlyingErrorKey`.

If you check the code of a system error, read it from the underlying error:

```swift
if let urlError = errorInfo.underlyingErrors.first as? URLError, urlError.code == .notConnectedToInternet {
    // ...
}
```

`cause` is now `nil` for these errors, because the system error is not an `ErrorInfo`. It remains set when the underlying error is an Ably error.

<h2 id="cipher-param-options">Pass cipher options as `ARTCipherParamOptions`</h2>

`ARTCrypto.getDefaultParams:` takes an `ARTCipherParamOptions` object, where it took a dictionary. The class has the dictionary's fields as typed properties: `key`, which is `NSData` or a base64-encoded `NSString`, and the optional `algorithm`, `keyLength` and `mode`.

```swift
// 1.x
let params = ARTCrypto.getDefaultParams(["key": key])

// 2.0
let params = Crypto.getDefaultParams(CipherParamOptions(key: key as NSData))
```

`ARTCipherParamsCompatible` is removed, so a dictionary can no longer be passed as a channel's `cipher` either. `ARTChannelOptions.initWithCipher:` takes only an `ARTCipherParams` object. Pass an `ARTCipherParamOptions` object to the new `initWithCipherOptions:` instead, or use `initWithCipherKey:` when you have only a key.

```swift
// 1.x
let options = ARTChannelOptions(cipher: ["key": key] as ARTCipherParamsCompatible)

// 2.0
let options = ChannelOptions(cipherOptions: CipherParamOptions(key: key as NSData))
```

`getDefaultParams:` now also raises `NSInvalidArgumentException` if `keyLength` does not match the key's length, or if `mode` is anything other than `CBC`. In 1.x the dictionary's `keyLength` and `mode` entries were ignored.

<h2 id="device-push-state">Read the push registration state as an enum</h2>

`ARTDevicePushDetails.state` is an `ARTDevicePushState`, where it was a nullable `NSString`. Its values are `ARTDevicePushStateActive`, `ARTDevicePushStateFailing` and `ARTDevicePushStateFailed`, which Swift sees as `.active`, `.failing` and `.failed`.

A fourth value, `ARTDevicePushStateUnknown`, takes the place of `nil`. The property has it when Ably reported no state, as for a device registration that did not come from Ably, or a state that this version of the SDK does not recognise.

Replace comparisons with the strings `"active"`, `"failing"` and `"failed"` with comparisons with these values, and replace `nil` checks with checks for `ARTDevicePushStateUnknown`.
